# soil_operator: a neural operator that learns a 1D soil-water solver

Status: research code. Not validated on real farms. Not used in production.

## What it is

1. `richards.py` (NumPy/SciPy) and `torch_richards.py` (PyTorch, differentiable) solve the
   1D Richards equation for water moving down a soil column (5 to 120 cm, two layers,
   van Genuchten soil, root uptake, free drainage at the bottom).
2. `synth.py`, `synth_blocks.py`, `synth_pairs.py` run that solver on thousands of
   randomly drawn made-up blocks (soil, roots, drip schedule, rain, ET) to make
   synthetic training data. Nothing is downloaded; the data is regenerated by the scripts.
3. `fno.py` + `train_fno.py` train a Fourier Neural Operator (FNO), optionally
   physics-informed (a water-balance penalty, "PINO" style; `--physics 0` turns it off),
   to copy the solver: inputs are water in at the top, ET, 12 soil and root numbers and a
   start profile; output is water content at 47 depths for every hour of a week.
   The solver is used only to make training data and, in the physics loss, as a water-balance check.
4. `check_fno.py`, `fit_soil*.py`, `fit_pairs.py` test, on synthetic data, whether soil
   numbers can be recovered by gradient descent through the FNO when only a few
   "probe" depths are shown, and how well saved water ("plants used it" vs "drained away")
   can be told apart with no probe.

Everything here that has a number attached was measured on synthetic data from the
project's own solver. The solver is "truth" in these tests, so they show the best case:
real fields are messier (3D drip wetting, wrong inputs, layered soil).

## What was learned (qualitative, from earlier work on one real probe site)

These came from running the plain solver on one real orchard probe dataset (not included
here, not reproducible from this folder):

- Fitting the soil numbers to the probe made the physics useful at that site.
- Soil numbers guessed from texture class alone were much worse than a plain average.
- The 1D column missed a large wetting event, probably drip or 3D effects that one column
  fed from one spot cannot represent.
- Fitted numbers hit the limits of their allowed ranges, so they should not be read as true soil properties.

One site, one probe column. Not a general result.

## Results on synthetic data

"Before vs after" test (`synth_pairs.py` + `fit_pairs.py`): 107 synthetic fields,
no probes, ET error +-12 %, meter error +-5 %, 2 seasons x 12 weeks, weeks 7-12 scored.
Median miss on the season's saved-drainage / plant-use estimate (lower is better):

| Setup (all synthetic) | one-season miss % | saved drain miss % | saved use miss % |
|---|---|---|---|
| true soil, no input errors (model limit) | 13 | 35 | 12 |
| true soil, steady errors | 20 | 39 | 19 |
| class-map soil, steady errors | 30 | 46 | 21 |
| class-map soil, mixed errors | 30 | 48 | 29 |
| class-map soil, changing errors | 30 | 53 | 46 |

Reading: even with the true soil, the drainage share is hard to pin down; with a coarse
soil class map it gets worse. These are first, small tests; treat as indications only.
(Numbers copied from a single run on GPU; not re-run here, so they are not seeds-averaged.)

## Quick smoke test (what was run for this release)

On CPU, torch 2.15 (CPU wheel), 3 training epochs on 24 synthetic weeks: the solver, data
generator, FNO training loop, `check_fno.py` and `fit_soil.py` all run end to end.
The FNO after 3 epochs is useless (kept-aside error about 0.085 m3/m3);
this only proves the scripts run.

## Requirements and how to run (CPU, small settings)

```bash
pip install torch --index-url https://download.pytorch.org/whl/cpu
pip install -r requirements.txt
cd experiments/soil_operator
./run_small.sh          # a few minutes: 48 samples, 3 epochs (smoke test only)
```

For something meaningful (hours on CPU, much faster on a GPU), scale up, for example:

```bash
python synth.py --n 20000 --out synth_20k.pt
python train_fno.py --data synth_20k.pt --epochs 200 --out fno_20k.pt
python check_fno.py --data synth_20k.pt --model fno_20k.pt

# several-week blocks, mixed into the training set, then fine-tune
python synth_blocks.py --blocks 2500 --weeks 8 --seed 11 --out blocks_train.pt
python merge_blocks.py --synth synth_20k.pt --blocks blocks_train.pt --out synth_mix.pt
python train_fno.py --data synth_mix.pt --init fno_20k.pt --epochs 60 --lr 0.0003 --out fno_mix.pt
python synth_blocks.py --blocks 300 --weeks 8 --out blocks_test.pt
python fit_soil.py --data blocks_test.pt --model fno_mix.pt

# no-probe tests
python synth_blocks.py --blocks 140 --weeks 16 --seed 23 --out blocks16.pt
python fit_soil2.py --data blocks16.pt --model fno_mix.pt
python synth_pairs.py --blocks 120 --weeks 12 --out pairs.pt
python fit_pairs.py --data pairs.pt --model fno_mix.pt
```

Generated `.pt` files are outputs; do not commit them. Training scripts use a GPU if present.

## ET input and your own data

By default the generators use a synthetic seasonal ET series (`synth.load_et_days`).
To use your own, give a CSV with one row per day and a column `et_mm_day`
(`ORCHARDWATER_ET_CSV=/path/et.csv python synth.py ...`).

`richards.load(csv_path)` reads your own hourly probe CSV with columns `time` (ISO
datetime), `theta_top` (water content at 5 cm, m3/m3) and `et_mm_day`, and `richards.run`
then simulates the column. The fitting scripts for such data were not included.

## Files

| File | What |
|---|---|
| `richards.py` | NumPy/SciPy solver (reference) |
| `torch_richards.py` | PyTorch solver (batched, differentiable) |
| `synth.py`, `synth_blocks.py`, `synth_pairs.py`, `merge_blocks.py` | synthetic data |
| `fno.py`, `train_fno.py` | FNO model and training (data loss + optional water-balance loss) |
| `check_fno.py` | accuracy and soil-recovery checks on synthetic data |
| `fit_soil.py` .. `fit_soil4.py`, `fit_pairs.py` | soil recovery / no-probe tests on synthetic data |
| `run_small.sh` | tiny CPU run |

The soil-class averages in `synth.py` are Rosetta class averages (Schaap et al. 2001).
